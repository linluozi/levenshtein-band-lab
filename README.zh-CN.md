# 中文说明

带裁剪窗口（banded）的 Levenshtein 距离，附带**实测**出来的 guard，以及一份能看清「哪个改动真正省了时间」的四臂基准。

## 这个项目要解决什么

网上讲 banded Levenshtein 的文章，通常给一个「优化版 vs 原版」的对比，然后报一个很大的加速比。问题是那个对比里优化版往往同时做了三件事：换滚动数组、加裁剪窗口、加长度差短路。三个功劳全记在「裁剪窗口」头上。

这个项目把三件事拆成四个臂，逐个隔离测量，然后只发布**永远不会比朴素实现更慢**的版本。

## 结论速览

| 问题 | 答案 |
|---|---|
| 长串上 band 快吗 | 快，n=320/k=2 时 39 倍，n=1024 时 125 倍 |
| 中文 2-4 字短词上快吗 | **不加 guard 会慢 1.1-1.4 倍** |
| 滚动两行省时间吗 | **不省**，只省内存（0.98 倍） |
| cutoff 很大时便宜吗 | **不便宜**，band 覆盖全宽，纯开销 |
| 真正的收益来自哪 | 裁剪窗口 + 行最小值早退，其余都是配套开销 |

## 四臂对照（每进程独立，n=320，k=2）

| 臂 | 做什么 |
|---|---|
| **A** | 全矩阵，每次调用重新分配（朴素基线） |
| **B** | 滚动两行，算满所有格子 |
| **C** | 裁剪窗口 + 行最小值早退，无 guard |
| **D** | 发布版：窗口 + 两个 guard |

| 场景 | B/A | C/B | D/C |
|---|---:|---:|---:|
| 近似匹配 | **0.98x** | **0.026x** | 0.99x |
| 提前拒绝 | 0.90x | 0.000x | 1.16x |
| 长度差拒绝 | 0.98x | 0.024x | 0.00x |

三个读数：

- **B/A ≈ 0.98x** —— 换滚动两行在时间上等于没变，纯粹是省内存。
- **C/B ≈ 0.026x** —— 那 39 倍全部来自裁剪窗口加早退。
- **长度差那一格的 D/C = 0.00x** —— 那个 case 一格 DP 都没算，一次 `abs()` 比较就返回了。把它报成「裁剪窗口的加速」是错的，任何人在基线前面加一行 `if` 都能拿到同样的数字。

## band 的收益是 n 和 k 的二元函数

只测一个点（n=320, k=2）恰好落在 band 的优势区，会把两处性能倒退完全掩盖。两处都画了图，也都在代码里加了 guard。

- k=2 时 band 从 n≈8 开始赢，且差距随 n 拉大：n=1024 时只有两行扫描耗时的 **0.8%**。
- 加宽 cutoff 会侵蚀优势：k=0-1 约 80 倍，k=20 约 10 倍，k=100 约 1.5 倍，k≈300 时打平。超过 `k = min(len(a), len(b))` 后 band 覆盖整个矩阵，纯属白付开销。

### 实测交叉点

`benchmarks/crossover.py` 每个点跑 31 轮交错、单次采样 ≥30 ms，并且要求 **中位数 < 0.90 且 p90 < 1.00** 才算 band 赢。严格口径很重要：轮数少的早期版本给出 k=2 时 n=6 交叉，31 轮后诚实答案是 n=8。

| cutoff k | band 从多长开始赢 | 代码里的 `BAND_MIN_LENGTH` |
|---|---:|---:|
| 0 | n ≥ 3 | 3 |
| 1 | n ≥ 5 | 5 |
| 2 | n ≥ 8 | 8 |
| 3 | n ≥ 9 | 9 |
| ≥4 | 每加 1 约多 2 个字符 | 外推 |

低于这些长度时 band 更慢：纯 Python 里每个 band 格子的成本约是紧凑内循环的 3-4 倍（要算 `lo`/`hi`、做两次边界重置、维护 `row_min`），短串上省下的格子抵不过这些开销。

## 两个 guard

```python
shorter = min(len(a), len(b))

# guard 1：长度差已经超预算，直接否
if abs(len(a) - len(b)) > max_distance:
    return None

# guard 2：band 覆盖全宽，机器白搭
# guard 3：串太短，band 的记账开销收不回来
if max_distance >= shorter or shorter < _band_min_length(max_distance):
    return _two_row_at_most(a, b, max_distance)
```

**guard 用路径断言验证，不用秒表。** 短串耗时是 1-20 微秒，接近计时噪声，测出来的「赢」在两次运行之间能翻符号。`tests/test_dispatch.py` 用调用计数器包住内部 kernel，断言**走的是哪条路径**：

```
长度低于交叉点 -> 走两行路径（不进 band）
长度达到交叉点 -> 走 band 路径
k >= min(len)  -> 走两行路径
```

这是确定性的，秒表失灵时它依然可查。

## 内存：唯一没有争议的收益

峰值辅助内存（`tracemalloc`，min-of-5）：

| n | 全矩阵 | 两行 | banded k=2 |
|---:|---:|---:|---:|
| 64 | 34.2 KiB | 1.7 KiB | 1.1 KiB |
| 256 | 530.1 KiB | 6.2 KiB | 4.2 KiB |
| 1024 | 26.1 MiB | 64.4 KiB | 16.4 KiB |
| 2048 | **130.2 MiB** | 144.4 KiB | **32.4 KiB** |

`O(min(m, n))` 与文档一致。注意 band 版仍然分配全宽行缓冲，空间是 `O(m)` 而不是教科书 Ukkonen 的 `O(k)`；把索引改到 band 内偏移还能再省一个量级。docstring 里写的和代码实际做的一致。

## 什么时候该用

**适合**

- cutoff 固定且小（`k ≤ 5`），串长超过约 10 个字符。
- 近似去重、拼写检查、标题/地址的模糊 join。
- 内存敏感：n=2048 时 130 MiB 降到 32 KiB。

**不适合**

- 搜索框里的中文 2-4 字短词。guard 会静默把你路由到两行扫描，等于没有加速 —— 直接用朴素扫描即可。
- cutoff 很大（k 与串长同量级）。同样被 guard 路由走。
- 需要长串的精确距离且没有 cutoff。用 `levenshtein_distance`，band 不适用。

## 语义

- 区分大小写。
- 按 Python Unicode 码点计算，不按字素簇。`"a\u0301"` 与 `"\u00e1"` 距离是 2 不是 0 —— 不做规范化。
- 插入、删除、替换各计 1。换位**不**算一次操作（那是 Damerau-Levenshtein，另一个度量）。

## 运行

```bash
python -m unittest discover -s tests -t .                 # 完整：约 2 分钟
LEVLAB_FAST=1 python -m unittest discover -s tests -t .   # CI：<1 秒

python benchmarks/run_all.py             # 完整基准 -> results.json
python benchmarks/run_all.py --quick     # 冒烟 -> results-quick.json
python benchmarks/run_all.py --isolated  # 每臂独立进程
python benchmarks/crossover.py           # 高重复交叉点测量
```

`--quick` 只写 `results-quick.json`，绝不覆盖 `results.json` —— 冒烟跑不能把正式测量表冲掉。

## 基准方法学

五条规则，每条都对应本项目踩过的一个坑：

1. **报比值，不报毫秒。** 同一进程内跨 case 的绝对耗时能漂 3 倍（分配器状态累积；一次 320×320 矩阵约 10 万个对象）。轮内比值能把漂移约掉。
2. **臂要交错跑。** 跑完 A 再跑 B，CPU 降频和背景负载会全落在后跑的一边。
3. **只做相邻对照。** 「优化版 vs 原版」藏住了优化版到底改了几件事，必须报每对相邻臂的比值。
4. **头条数字用 `--isolated`。** 每臂一个解释器，彻底消除跨 case 污染。
5. **耗时取 best-of-N，`tracemalloc` 取 min-of-N。** 干扰只会让单次变慢，最小值是被污染最少的样本。

换机器复现前不要直接引用这里的数字。曲线形状稳定，但绝对交叉点随解释器版本和 CPU 变化。
